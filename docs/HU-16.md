# HU-16: Registrar punto seguro y horario

Como comprador o vendedor, quiero registrar un punto seguro y un horario para organizar una entrega presencial.

## Criterios de aceptación

1. Los participantes pueden registrar `safePointId` y `scheduledTime`.
2. Cuando se acuerda el encuentro, la transacción pasa a `AGREED_POINT`.
3. Una persona ajena a la transacción no puede modificarla.

## Implementación

La API ya expone `POST /api/transactions/:id/confirm-point` con `{ safePointId, scheduledTime }`. Esta HU agrega la interfaz web para usarlo.

- `/transacciones` (nueva, requiere sesión): lista las compras y ventas del usuario con `GET /api/transactions`. Muestra el estado y, si falta, el aviso "Falta acordar punto y horario". Se llega desde el enlace **Transacciones** del encabezado.
- `/transacciones/:id` (nueva, requiere sesión): detalle con `GET /api/transactions/:id`. Si la transacción está en `PENDING`, muestra el formulario para elegir el punto seguro y la fecha y hora del encuentro. Si ya hay encuentro acordado, muestra el lugar y la hora.
- Al iniciar una compra (HU-15), el aviso de éxito incluye el enlace **Acordar punto seguro y horario**.
- `web/src/lib/safePoints.ts`: catálogo de puntos seguros de Cali. La API guarda `safePointId` como texto y todavía no tiene un recurso de puntos seguros, así que la web ofrece una lista cerrada con identificadores del mismo formato que el seed (`cai-granada`).
- `web/src/lib/api.ts`: `transactionApi.list`, `get` y `confirmPoint`, y los campos `safePointId`, `scheduledTime`, `product`, `buyer` y `seller` en el tipo `Transaction`.

La hora se elige en la zona horaria del navegador y se envía en ISO 8601 (UTC). La web exige elegir un punto y una fecha futura antes de enviar. Si otra persona confirmó primero (409), se muestra el aviso y se recarga la transacción. Si quien abre la página no es comprador ni vendedor (403), se muestra que no puede verla ni modificarla y no aparece el formulario.

## Validación manual

Con la base de datos, la API y la web encendidas según el README:

1. Iniciar una compra (HU-15) con una cuenta compradora y abrir **Acordar punto seguro y horario**.
2. Enviar el formulario vacío: debe pedir el punto seguro. Elegir una fecha pasada: debe pedir una fecha futura.
3. Elegir un punto y una fecha futura y confirmar. Verificar el aviso de éxito, el estado **Punto acordado** y el lugar y la hora mostrados. En `GET /api/transactions/:id`, comprobar `status: AGREED_POINT`, `safePointId` y `scheduledTime`.
4. Ingresar con la cuenta vendedora: en **Transacciones** debe verse la misma transacción con el encuentro acordado y sin formulario.
5. Repetir con una transacción nueva, pero confirmando desde la cuenta vendedora: también debe permitirlo (criterio 1).
6. Ingresar con una tercera cuenta y abrir `/transacciones/:id` de esa transacción: debe mostrar que no participa. Un `POST /api/transactions/:id/confirm-point` directo con su JWT debe devolver 403 (criterio 3).
7. Abrir la página en dos pestañas (comprador y vendedor) y confirmar en ambas: la segunda debe mostrar el aviso de conflicto y recargar el encuentro ya acordado.

## Pruebas existentes del backend

`back/src/transaction/transaction.service.spec.ts` cubre que `confirmPoint` guarda el punto y el horario y cambia a `AGREED_POINT`, y que rechaza fechas inválidas, no participantes y transacciones que no están en `PENDING`.

`back/test/transaction.e2e-spec.ts` cubre el 403 para terceros, el 400 por cuerpo inválido, el 200 con el cambio a `AGREED_POINT` y el 409 al repetir la confirmación.
