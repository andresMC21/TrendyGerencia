# HU-08: Publicar un producto

Como vendedor autenticado, quiero crear una publicación con datos y ubicación para ofrecer un artículo a personas cercanas.

**Criterios de aceptación**

1. Con título, descripción, categoría, condición y ubicación válidos, se publica el producto.
2. El nuevo producto queda disponible (`AVAILABLE`) y vinculado al vendedor.
3. Los datos inválidos se rechazan; publicar sin JWT devuelve 401.

Referencia del informe de solución: la tarjeta D4 («Publicación») valida que la persona publique un objeto sola en menos de 60 segundos. Según el modelo de negocio, publicar es gratis (V1).

### Debilidades encontradas

| Debilidad | Impacto |
|---|---|
| `title`, `description`, `category` y `neighborhoodId` no se recortaban. Con `"   "` se superaban `@IsNotEmpty` y `@MinLength(3)`. | Se podían publicar productos con título o descripción vacíos. Esto incumple el criterio 3. |
| `GeoPointDto` usaba solo `@IsLatitude/@IsLongitude`, que aceptan strings (`"3.45"`). | Llegaban strings a la columna PostGIS. El tipo dejaba de coincidir con el contrato. |
| `location: null` o `"Cali"` dependían del comportamiento implícito de `@ValidateNested`. | Los mensajes de error eran poco claros y no había una regla explícita. |
| `neighborhoodId` aceptaba cualquier texto (`"San Fernando "`, `"barrio_#1"`). La categoría distinguía mayúsculas. | El filtro hiperlocal por barrio fallaba: el feed compara `neighborhoodId` con igualdad exacta. |

| Un fallo de guardado devolvía un 500 genérico sin registro. | No había trazabilidad ni un mensaje coherente. |
| Pruebas: solo dos casos unitarios de `create`. No había pruebas del DTO ni del 401 fuera de e2e. | Los criterios 2 y 3 quedaban sin cobertura en la suite unitaria. |

### Pendientes fuera del alcance de HU-08

- **Fotos del producto.** El informe (5.4) menciona la fotografía en el flujo de publicación. La API no tiene almacenamiento de imágenes, y añadirlo exige migración e infraestructura de archivos. Queda propuesto como una HU aparte.
- **Módulo de barrios.** `neighborhoodId` sigue siendo un slug libre (hay un `TODO: FK a Neighborhood` en la entidad). Pertenece al módulo de barrios (HU-09, «Explorar el barrio»). La web usa un catálogo provisional.

## 2. Cambios implementados

### Backend (`back/src/product`)

- **`dto/create-product.dto.ts`**
  - Recorta `title` y `description` antes de validar.
  - Normaliza `category` y `neighborhoodId` a minúsculas y sin espacios externos.
  - Exige que `neighborhoodId` sea un slug (`^[a-z0-9]+(-[a-z0-9]+)*$`) de hasta 60 caracteres.
  - Declara `location` como obligatoria con `@IsDefined` y `@IsNotEmptyObject` antes de `@ValidateNested`.
  - Amplía la documentación Swagger.
- **`dto/geo-point.dto.ts`**: `lat` y `lng` deben ser números finitos (`@IsNumber`) y estar en rango.
- **`product.service.ts`** (`create`)
  - Copia los campos de forma explícita en lugar de esparcir el DTO.
  - Fija el vendedor desde el JWT y el estado en `AVAILABLE`.
  - Si falla el guardado, registra el error con `Logger` y responde `InternalServerErrorException` con un mensaje en español. En ese caso no invalida la caché.
- **`product.controller.ts`**: la documentación de `POST /products` explica el 401, los campos prohibidos (`sellerId`, `status`) y la normalización.
- **Pruebas nuevas o ampliadas**
  - `dto/create-product.dto.spec.ts` (nuevo). Valida con la misma configuración del `ValidationPipe` global:
    - cuerpo válido, mínimo y normalizado;
    - falta de cada campo obligatorio;
    - textos vacíos, demasiado largos o con espacios;
    - slug inválido y condición fuera del catálogo;
    - lat/lng fuera de rango o como string, y `location` nula, vacía o string;
    - precio negativo o con 3 decimales, booleano inválido y peso 0;
    - `sellerId`, `status` y `viewsCount` prohibidos.
  - `product.create.http.spec.ts` (nuevo). Integración HTTP con supertest **sin base de datos**: guard real de Passport + `JwtStrategy`, `ValidationPipe` real y `ProductService` simulado. Cubre:
    - 201 vinculado al vendedor del JWT;
    - 401 sin token, con token mal formado, con otra firma, con esquema distinto de Bearer, con sesión cerrada y con cuenta inactiva;
    - 400 con datos inválidos;
    - 400 si se envía `sellerId` o `status`.
  - `product.service.spec.ts`: dos casos nuevos. Uno comprueba que se ignoran los campos ajenos y se fuerza `AVAILABLE` con el vendedor del JWT. El otro comprueba el 500 controlado sin invalidar la caché.

> Nota: `UpdateProductDto` hereda de `CreateProductDto` mediante `PartialType`. Por eso la edición también recorta y normaliza los campos que se envían. El comportamiento de HU-13 y de la edición no cambió: solo se impide guardar datos que la publicación ya rechaza.


### Prueba manual con la API (Swagger o Postman)

Con la base de datos y la API encendidas según el README, inicia sesión con `POST /api/user/login` y copia el `token`.

1. **Publicación válida → 201**
   ```http
   POST /api/products
   Authorization: Bearer <token>
   Content-Type: application/json

   {
     "title": "  Bicicleta MTB  ",
     "description": "Rin 26, poco uso",
     "category": "Deportes",
     "condition": "COMO_NUEVO",
     "location": { "lat": 3.4516, "lng": -76.532 },
     "neighborhoodId": "granada",
     "price": 250000,
     "acceptsBarter": true
   }
   ```
   Esperado: `status: "AVAILABLE"`, `sellerId` igual al id del usuario del token, `title: "Bicicleta MTB"`, `category: "deportes"`.
2. **Datos inválidos → 400.** Por ejemplo, `title: "   "`, `condition: "ROTO"`, `location: { "lat": 99, "lng": 0 }` o `location: { "lat": "3.4", "lng": -76 }`. `message` lista cada campo.
3. **Campos que fija el servidor → 400.** Si se añade `"sellerId": "..."` o `"status": "SOLD"`, la respuesta incluye `property sellerId should not exist` y `property status should not exist`.
4. **Sin JWT → 401.** El mismo cuerpo del caso 1, sin la cabecera `Authorization`, también devuelve 401 con un token alterado o después de `POST /api/user/logout`.

### Prueba manual en la web

1. Ingresa y usa el enlace **Publicar** del encabezado (`/publicar`).
2. Envía el formulario vacío: cada campo muestra su error y no se hace ninguna petición.
3. Completa título, descripción, categoría, condición y barrio, y publica. Debe aparecer «¡Tu producto quedó publicado!» con el estado «Disponible». «Ver publicación» abre el detalle.
4. Con la sesión vencida o revocada desde otra pestaña, publicar muestra «Tu sesión expiró» con el enlace para ingresar.
5. Abre `/publicar` sin sesión: la ruta redirige a `/ingresar`.
