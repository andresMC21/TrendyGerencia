# HU-15: Iniciar una transacción

Como comprador autenticado, quiero iniciar la compra o el trueque de un producto para comenzar un intercambio con su vendedor.

## Implementación

Desde `/producto/:id`, el comprador puede iniciar una transacción y escribir un mensaje opcional de hasta 500 caracteres. Si la publicación acepta trueque, el formulario permite proponer el intercambio en ese mensaje, según el contrato actual de la API.

El cliente envía `POST /api/transactions` con el JWT y `{ productId, message? }`. El servidor determina el comprador a partir de la sesión y el vendedor a partir del producto. Crea la transacción en `PENDING` y reserva el producto. La interfaz muestra la referencia creada y actualiza el estado del artículo.

La página solicita iniciar sesión a los visitantes, impide comprar una publicación propia y no permite iniciar sobre productos no disponibles. Los errores del servidor se muestran en el formulario; si hay un conflicto, se vuelve a consultar el producto.

## Validación manual

Con la base de datos, la API y la web encendidas según el README:

1. Publicar un artículo disponible con una cuenta de vendedor.
2. Ingresar con otra cuenta, abrir el artículo e iniciar la compra. Verificar la confirmación `PENDING`, la referencia y el estado reservado. En `GET /api/transactions`, comprobar `productId`, `buyerId` y `sellerId`.
3. Abrir otro artículo disponible que acepte trueque y enviar una propuesta en el mensaje. Comprobar que se conserva en la transacción.
4. Abrir una publicación propia: debe aparecer la explicación y no el formulario. Un intento directo desde la API debe devolver 403.
5. Abrir un artículo reservado o vendido: no debe permitir iniciar una transacción. La API debe devolver 409 si se intenta directamente.
6. Abrir el detalle sin sesión: debe ofrecer el enlace para ingresar. La API sin JWT debe devolver 401.
7. Hacer clic repetido al enviar: el botón debe quedar desactivado durante la solicitud y desaparecer al confirmar.

## Pruebas existentes del backend

`back/src/transaction/transaction.service.spec.ts` cubre la creación en PENDING con los participantes correctos, compras propias, productos no disponibles, transacciones activas y recuperación ante un fallo de guardado.

`back/test/transaction.e2e-spec.ts` cubre autenticación, validación del cuerpo, creación y reserva, permisos y conflictos. Las pruebas e2e requieren PostgreSQL/PostGIS configurado para pruebas; consultar el README antes de ejecutarlas.
